# 文档写作指南

当文档修改范围较大、需要刻意设计结构或审查覆盖范围时阅读本指南。它补充 `SKILL.md` 中的简短路由规则。

## 确定本地化语言

英语始终是第一语言和规范方向。写作前，从置信度最高的证据推理且仅确定一种本地化语言：用户明确要求、仓库说明、
已有文件名配对、本地化配置，以及面向相同读者的相邻文档。不要默认中文、用户语言或最常见的语言。如果证据冲突，
或无法确认本地化语言，在创建或修改文档前询问用户。确定后保留英语文件及其本地化翻译，并保持语义一致；代码、
命令、标识符和链接保持原样。

## 注释语义覆盖

针对每个消费者可见的代码元素，检查读者实际看到的声明、schema 或行为。这包括函数、类、方法、构造器、字段、属性、
类型、枚举分支、事件、命令、配置键、schema 和状态转换。说明性注释或 docstring 必须先完整使用英语，再写本地化语言
的完整对应版本，不要交错两种语言的句子。

合格的注释通常包含摘要，并在适用时说明：

- 每个输入、字段、选项或分支的语义角色；
- 可选性、默认值、单位、有效范围、所有权和可变性；
- 生命周期、顺序、副作用、时序、重试和取消；
- 输出、身份、缓存、资源清理和结果表示；
- 失败、被拒绝的组合、安全约束和兼容性边界；
- 泛型值、重载、状态或相关声明之间的关系。

使用项目已有语法。语言或工具提供的结构化标签（例如 JSDoc 或 TSDoc）只是承载手段，不是事实来源。结构化字段只
保留一份，在每个字段描述中同时提供英语和本地化语言，并确保忽略这些标签后正文仍完整。不要只复述类型或签名。

例如，正文先使用完整英语语言块，再使用完整本地化语言块，标签保持结构唯一。本地化语言块始终位于英语之后：

```ts
/**
 * Loads the configuration file and validates its schema.
 * The returned object is detached from the parser's internal state.
 *
 * 加载配置文件并校验其 schema。
 * 返回对象与解析器的内部状态分离。
 *
 * @param path Path to the configuration file. 配置文件路径。
 * @returns A validated configuration. 已校验的配置。
 */
```

## Markdown 结构

按读者意图而不是源码树形状选择页面：

| 读者需求 | 最合适的文档表面 |
| --- | --- |
| 这是什么，如何开始？ | README 或概览 |
| 概念如何工作？ | 聚焦的概念页面 |
| 如何完成某项任务？ | 配方或指南 |
| 如何从旧版本迁移？ | 迁移页面或变更日志 |
| 为什么失败？ | 排错页面 |

保持每页聚焦。通过链接指向相邻页面，不要复制契约。使用稳定的标题层级、描述性链接文本、带正确语言标记的
代码块，并明确示例的输出或限制。每个面向人的页面、段落、示例说明和变更日志条目都必须先提供英语版本，再提供
语义等价的本地化语言版本。

## 证据和审查

将声明追溯到实现、类型、测试、配置或明确的外部权威来源；假设要明确标注。审查 diff 中的过时 API 名称、
没有依据的承诺、缺失链接、不再运行的示例，以及意外变成 Agent 指令的文字。确定本地化语言后，比较两份文件的范围
和安全边界，而不只是标题是否匹配。
