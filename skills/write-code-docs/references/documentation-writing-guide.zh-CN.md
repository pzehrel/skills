# 文档写作指南

当文档修改范围较大、需要刻意设计结构或审查覆盖范围时阅读本指南。它补充 `SKILL.md` 中的简短路由规则。

## 确定本地化语言

英语始终是第一语言和规范方向。写作前，从置信度最高的证据推理且仅确定一种本地化语言：用户明确要求、仓库说明、
已有文件名配对、本地化配置，以及面向相同读者的相邻文档。不要默认中文、用户语言或最常见的语言。如果证据冲突，
或无法确认本地化语言，在创建或修改文档前询问用户。确定后保留英语文件及其本地化翻译，并保持语义一致；代码、
命令、标识符和链接保持原样。

## 翻译保真度

英语在前是为了便于 Agent 发现信息，并为审阅者提供稳定的事实来源；这不允许本地化版本变成改写。先完整、忠实地翻译英语语言块，
再比较两份语言块是否存在：

- 遗漏或增加声明、限定、示例或约束；
- 否定、确定性、义务、许可、数量或条件范围发生变化；
- 同一概念的术语不一致；
- 代码 token、路径、命令、标识符、链接或错误码被改动。

可以使用自然语法，但不能弱化、强化或编辑性改写技术含义。英语来源存在歧义时应标记或询问用户，不要静默替它做决定。人类审阅检查保真度和可读性，
不是独立重写的授权。

## Agent 指令文档

`AGENTS.md` 是文档表面，也可能具有权威性。将其中的规则写成明确且有范围的 prose：说明触发条件、所需动作、例外和验证方式。
将持久规则与项目背景、临时状态分开。本指南负责清晰度、语义覆盖和双语呈现；规则准入以及层级或范围变更仍以仓库的 Agent 说明维护流程为准。

规范 `AGENTS.md` 使用英语供 Agent 消费。精准的人类审阅翻译放在仓库约定的本地化对应文件中，例如 `AGENTS.zh-CN.md`，并在有用时
互相链接。本地化对应文件不会自动具有权威性或可发现性；只有相关 harness 明确记录会加载它时，才把它视为生效说明。

## 注释语义覆盖

检查相关实现的整体，而不只是导出的函数。针对每个消费者可见的代码元素，检查读者实际看到的声明、schema 或行为。这包括函数、类、方法、构造器、字段、属性、
类型、枚举分支、事件、命令、配置键、schema 和状态转换。说明性注释或 docstring 必须先写完整的英语语言块，空一行后再在同一个注释或
docstring 块中写本地化语言的完整对应版本。本地化语言块直接开始，不要添加诸如 `Chinese:` 或 `中文：` 的语言标签。不要把两种语言拆到
相邻注释块中，也不要交错两种语言的句子。

### 文件级头部

每个新建或实质性修改的代码文件（源代码、可执行脚本、配置或 schema）都应在文件顶部添加一段简洁的双语头部。头部放在导入和声明之前，
但要放在 shebang、编码标记等语法要求的行以及仓库要求的许可证头部之后。头部应告诉维护者：

- 文件负责什么，以及明确不负责什么；
- 在不显然时，主要输入、输出、集成关系或副作用是什么；
- 适用时，解释文件存在理由的稳定不变量或边界。

使用该语言的模块 docstring 或最接近的文件级注释形式。完整英语块始终位于前面，空一行后在同一注释/docstring 中放置完整本地化语言块。
头部应简短且持久：它用于帮助定位，不是变更日志、符号索引或重复的 API reference。文件职责或边界变化时更新头部。不要为生成文件或
vendor 文件添加头部，也不要在仓库明确禁止头部时添加；必需的许可证、工具和构建指令必须原样保留。

例如，TypeScript 文件可以在导入之前使用单个 JSDoc 头部：

```ts
/**
 * Coordinates retry policy construction and validation for outbound requests.
 * This module does not perform requests or persist policy state.
 *
 * 负责构建和校验出站请求的重试策略。
 * 本模块不执行请求，也不持久化策略状态。
 */

import { validate } from './validation';
```

合格的注释通常包含摘要，并在适用时说明：

- 每个输入、字段、选项或分支的语义角色；
- 可选性、默认值、单位、有效范围、所有权和可变性；
- 生命周期、顺序、副作用、时序、重试和取消；
- 输出、身份、缓存、资源清理和结果表示；
- 失败、被拒绝的组合、安全约束和兼容性边界；
- 泛型值、重载、状态或相关声明之间的关系。

也要审查私有代码和内部代码。当私有声明或实现代码块的用途、不变量、修改、顺序、错误转换、兼容性、资源或生命周期、性能或
安全约束无法从局部代码中显然看出时，添加注释。为复杂算法、状态转换、嵌套分支、有意义的循环边界或退出条件、数据转换、正则表达式、
不显然的常量、同步或重试逻辑以及清理路径添加注释。将注释放在需要解释的最小代码块旁边，并说明代码为何采用这种形态。跳过简单包装器、
直接赋值和显然的控制流。先对导出符号和私有符号执行覆盖检查，再对实现主体执行复杂度检查。

### 结构化数据的字段级覆盖

对于消费者可见的 interface、对象类型、record、dataclass、struct、类属性集合、枚举式对象、配置/选项对象、序列化载荷或 schema，
要在声明处记录每个字段/属性/成员/键。类型级摘要可以提供上下文，但不能代替字段文档；字段名和类型本身都无法完整表达契约。
对于语义属于消费者契约的每个字段，说明其语义角色，并在适用时说明可选性或可空性、默认值、单位、有效范围、所有权/可变性、
序列化或省略行为、生命周期、兼容性，以及涉及其他字段的关系或约束。对消费者可见的嵌套对象也要递归执行同样的检查。

使用语言或文档工具最接近的字段级形式：TypeScript 属性上方的内联 JSDoc/TSDoc、Python dataclass 的属性注释/docstring、Go/Rust
struct 字段注释、Java/Kotlin/C# 属性或 record 组件注释，或 OpenAPI/JSON Schema/protobuf/SQL/配置元数据中的 description。如果格式
无法将描述附加到字段，就在最近的权威 schema/表格/参考文档中记录字段，并从声明处链接或保持同步。不要因为字段看起来不言自明就跳过；
只有遵循仓库约定的真正私有简单字段才可省略。

例如，每个 TypeScript 属性都应有自己的双语块，而不能只依赖 interface 注释：

```ts
interface RetryOptions {
  /**
   * Maximum number of attempts, including the initial call. Must be at least 1; defaults to 3.
   *
   * 最大尝试次数，包括首次调用。必须至少为 1；默认值为 3。
   */
  maxAttempts?: number;

  /**
   * Delay between attempts in milliseconds. A value of 0 retries immediately.
   *
   * 重试之间的延迟，单位为毫秒。值为 0 时立即重试。
   */
  delayMs?: number;
}
```

使用项目已有语法。语言或工具提供的结构化标签（例如 JSDoc 或 TSDoc）只是承载手段，不是事实来源。结构化字段只
保留一份；每个字段描述先写英语，空一行后再写不带语言标签的本地化语言。确保忽略这些标签后正文仍完整。不要只复述类型或签名。

例如，正文先使用完整英语语言块，空一行后再使用不带语言标签的完整本地化语言块，标签保持结构唯一。本地化语言块始终位于英语之后：

```ts
/**
 * Loads the configuration file and validates its schema.
 * The returned object is detached from the parser's internal state.
 *
 * 加载配置文件并校验其 schema。
 * 返回对象与解析器的内部状态分离。
 *
 * @param path Path to the configuration file.
 *
 *   配置文件路径。
 * @returns A validated configuration.
 *
 *   已校验的配置。
 */
```

## Markdown 本地化布局

Markdown 本地化默认使用独立文件，每个文件只使用一种 prose 语言：

```text
README.md
README.<locale>.md
docs/configuration.md
docs/configuration.<locale>.md
```

仓库已有 locale 目录约定时遵循该约定。英语文件和本地化文件必须具有对等的标题、表格、链接、示例、代码块、条件和安全边界。
不要把代码注释的布局复制到 Markdown 中，在单个文件内交替英语和本地化段落。只有仓库或用户有明确规则时，才使用内联双语 Markdown。

## Markdown 结构

按读者意图而不是源码树形状选择页面：

| 读者需求 | 最合适的文档表面 |
| --- | --- |
| 这是什么，如何开始？ | README 或概览 |
| 概念如何工作？ | 聚焦的概念页面 |
| 如何完成某项任务？ | 配方或指南 |
| 如何从旧版本迁移？ | 迁移页面或变更日志 |
| 为什么失败？ | 排错页面 |

保持每页聚焦。通过链接指向相邻页面，不要复制契约。使用稳定的标题层级、描述性链接文本、带正确语言标记的
代码块，并明确示例的输出或限制。每个面向人的页面、段落、示例说明和变更日志条目都必须先提供英语版本，再提供
语义等价的本地化语言版本。

## 证据和审查

将声明追溯到实现、类型、测试、配置或明确的外部权威来源；假设要明确标注。审查 diff 中的过时 API 名称、
没有依据的承诺、缺失链接、不再运行的示例，以及意外变成 Agent 指令的文字。确定本地化语言后，比较两份文件的范围
和安全边界，而不只是标题是否匹配。
