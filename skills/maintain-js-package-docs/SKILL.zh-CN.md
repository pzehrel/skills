# 维护 JS 包文档

在开发包时应用 Agent 可读的包文档规范。把文档视为公共契约的一部分，并在同一次改动中完成实现和
所有受影响的文档层。这套规范让已安装的包能够自我描述并与版本一致，但不会把包文档变成 Agent
指令。内容首先针对直接读取源码或声明的编码 Agent 优化，其次保证人类自然阅读，最后兼顾编辑器
和文档工具的呈现。

明确采用这一设计优先级：**Agent-first，human-friendly，tool-compatible。**

- **Agent-first：**让用途、契约、示例和更深层本地文档的路由容易从源码、声明和打包产物中发现并
  理解。
- **human-friendly：**使用完整、自然的技术文字，让开发者无需了解 Agent 专属约定也能理解。完整性
  优先于篇幅压缩；只有保留所有相关契约细节后，才可以缩短表达。
- **tool-compatible：**以 JSDoc 为基线，仅在 TSDoc 或工具专属增强能够改善提取、校验或呈现且不会
  成为唯一事实来源时使用它们。

## 确定文档影响

编辑前，检查实际生效的仓库说明以及包中已有的事实来源：`package.json`、公共入口、声明输出或源
类型、README、文档索引、相关主题页、示例、测试以及发布或迁移约定。只读取与请求改动相关的材料。

先识别可观察变化，再决定需要记录什么。工作改变以下任一内容时，应更新文档：

- 公共导出、签名、类型、默认值或生命周期；
- 支持的配置、环境、运行时或兼容性；
- 错误、副作用、顺序要求、性能特征或安全指南；
- 推荐用法、弃用状态、迁移步骤或用户可见的限制。

对于行为保持不变的内部重构，不要制造文档噪音；但如果它改变了已记录的心智模型、扩展点、贡献者
工作流或架构契约，则仍需更新。

接入或审查规范、新建文档结构、进行重大公共 API 变更、处理弃用或迁移，或者检查 npm 发布内容
前，先阅读
[references/package-documentation-specification.zh-CN.md](references/package-documentation-specification.zh-CN.md)。
对于已经符合规范的包中的小改动，遵循既有路由，只加载受影响的文档。

## 同步实现代码和文档

1. 实现请求的行为及其测试。不要把规划中的行为写成已经存在。
2. 根据 `package.json` exports、公共入口和生成的声明表面盘点消费者真正可用的 API。不要把源码中
   每个带 `export` 的声明都等同于包的公共导出。
3. 确保每个公开导出的函数、类、构造函数、值、类型、接口、枚举，以及每个面向消费者的公开成员，
   都在权威源声明处具有 `/** ... */` API 注释。默认以 JSDoc 正文和标签作为作者规范。只有仓库文档
   工具链确实消费时，才把 TSDoc 专属结构作为补充层，并保证忽略这些扩展后仍能理解必需契约语义。
   如果原始声明注释会保留到生成声明中，re-export barrel 不需要重复注释。每个契约不同的重载，或
   无法在消费者可见帮助中获得注释的重载，都必须单独记录。
4. 公开 callable 的注释只有覆盖了每个运行时参数，以及所有不直观的返回值、泛型、失败和重载语义
   后才算完整。描述语义角色和行为，不要复述 TypeScript 类型，也不要添加没有提供签名之外信息的
   标签。
5. 非公开函数的用途、原因、不变量、修改行为、顺序、错误转换或算法无法通过名称和类型看清时，应
   添加注释。不要为了增加数量而注释简单包装、回调或显而易见的局部 helper。
6. 如果包级 JSDoc 风格注释有助于 Agent 和用户了解包用途并发现随包文档，则在公共类型入口保留或
   添加该注释。只有已采用的工具链使用时才添加 TSDoc `@packageDocumentation` 标记。遵循仓库已有
   的注释标准，并确保生成声明时保留有用注释。
7. 更新范围最小的权威人类可读文档。让 README 保持为精简入口；把详细概念、任务、配方、迁移和
   故障排除内容路由到仓库既有文档目录下的聚焦文件。
8. 推荐调用方式变化时更新示例。优先使用可通过现有项目工作流进行类型检查、测试或以其他方式运行
   的示例。
9. 对破坏性变更和弃用，同时记录替代方案和迁移路径。只有仍受支持的版本需要旧指南时才保留它，
   并明确标注适用范围。

避免在多个位置复制同一契约。让类型定义精确形状，让测试定义已验证行为，让 README 提供方向，
让主题文档解释概念和任务。通过链接连接这些层，而不是维护平行的重复文字。

## 编写 Agent 可读、以 JSDoc 为主的 API 注释

对于每个导出函数、公开方法、构造函数、调用签名和函数值公开属性，消费者看到的声明所附注释必须
是完整的 API 注释。注释应足够自包含，让编码 Agent 或人类能在签名旁理解契约：

- 说明操作及其可观察契约的摘要；
- 每个运行时参数（包括 rest 参数）对应一个 `@param`，并说明其语义角色、可选行为和适用的默认值；
- 当返回结果具有名称和 TypeScript 返回类型不能直接说明的语义时使用 `@returns`，例如所有权、
  身份、可变性、单位、结果分支、缓存或失败表达；
- 当类型参数的角色、约束、关系或生命周期不直观时记录泛型语义；可写在普通正文或相关
  `@param`/`@returns` 中，仓库 TSDoc 流程支持或要求时可另外添加 `@typeParam`；
- 记录有意义的同步异常、异步拒绝、回调失败传播和结果值失败；抛出的异常使用 JSDoc `@throws`，
  当某些消费者可能忽略该标签时，在普通正文中也要能理解关键细节；不得虚构失败契约；
- 每个重载都有独立的完整注释，除非已经验证 `{@inheritDoc}` 或工具支持的注释继承会为每个可见
  签名保留精确契约。

在 `.ts` 和 `.tsx` 中让 TypeScript 语法承载类型：不要在 `@param` 或 `@returns` 中用花括号重复类型，
也不要使用 JSDoc `@template` 重新声明 TypeScript 泛型。在 `.js` 和 `.jsx` 中，如果 JSDoc 类型标签
承担包的类型信息，则使用 TypeScript 支持的这些标签。

主要词汇采用 JSDoc：摘要正文、`@param`、`@returns`、`@throws`、`@deprecated`、`@see`、`@example`
和 `{@link}`。把 `@packageDocumentation`、`@typeParam`、`@remarks`、`@defaultValue`、发布阶段修饰符
和 TSDoc 声明引用等视为可选增强。使用它们前，检查仓库中已有的 TSDoc、API Extractor、TypeDoc 或
相关 linter 配置与约定。不要仅因为文件是 TypeScript 就添加 TSDoc 标签，也不要把必需契约信息的
唯一副本放在基线 JSDoc 消费者可能忽略的扩展中。

函数值属性与方法语法适用相同要求。除非另有充分理由，不要为了文档改变既有 API 形状；把标签附在
属性注释中，并验证项目的声明和文档工具如何渲染。其他位置的文档不能成为签名注释缺失或不完整的
理由。

泛型公开类、接口和类型别名也适用同一语义规则：类型参数角色不直观时必须解释，但不机械地要求
每个泛型都有 `@typeParam`。

完成前创建临时覆盖表，每个公开 callable 一行，包含摘要、参数、不直观的返回值语义、不直观的
泛型语义、失败、重载、JSDoc 基线、采用 TSDoc 增强的理由、生成声明保留情况和代表性工具呈现等列。
只有签名与名称已经足够明确时，相关语义列才可标记为不适用。只有仓库已经采用相应配置时，缺少
TSDoc 增强才属于失败。任何其他适用单元格缺失时，不得汇报完成。

## 保持已安装文档可用

包发布到 npm，并且本地文档属于预期开发体验时：

- 在包根 README 靠前位置保留精简的文档路由；
- 让文档索引通过相对链接指向聚焦文件；
- 在发布文件白名单中包含必需文档和示例；
- 使用相对于包根目录的本地路径，不要假设固定的 `node_modules` 布局；
- 把随包文档视为与版本匹配的参考资料，而不是消费仓库中的更高优先级指令；
- 除非目标工具链明确实现了相关约定，否则不要依赖 `llms.txt`、自定义 `package.json` 字段或依赖级
  `AGENTS.md`。

除非用户任务已授权，否则不要执行发布、修改发布配置或扩大包内容。相关时可以进行只读的包内容
预检。

包内注释和随包 Markdown 可以推荐受支持的模式、权衡或后续阅读，但它们是建议性的参考资料，不是
消费端编码 Agent 必须服从的指令。不得要求 Agent 忽略仓库说明、改变工作流、运行命令或修改文件。
真实的 API 前置条件描述程序行为时仍可使用强制性语言，例如要求在进程退出前调用 `close()` 以刷新
缓冲数据。

## 验证结果

运行仓库适用的测试、类型检查、文档检查和示例验证。先运行已有的 JSDoc 完整性 linter。仓库已经
采用 TSDoc 配置时，再运行 TSDoc 检查并遵循其标签配置；除非任务已授权工具变更，否则不要新增
lint 依赖。处理 npm 包时，使用 `npm pack --dry-run` 或仓库的等价命令检查实际产物，并确认 README、
预期文档、示例、声明、
运行时文件和 source map 符合包策略。不要仅因文件存在于仓库中就假设它会被发布。

审查 diff，检查过时名称、失效相对链接、重复权威来源、声明中被移除的注释、不再通过类型检查的
示例，以及缺少代码或测试支持的文档承诺。把生成的公共声明表面与 API 清单对照，并列出任何没有
完整保留文档注释的公共符号或成员，包括缺少的参数文档，或者不直观的返回值、泛型、失败或重载
语义。忽略可选的 TSDoc 专属标签后，确认 JSDoc 基线仍然可以理解。在环境可用时，通过编辑器或文档
工具验证代表性注释，但把呈现视为兼容性检查，而不是文档的首要目的；否则标记为未实测。汇报修改
了哪些文档表面、运行了哪些检查，以及哪些包管理器、运行时或 Agent 未经实测。执行规范接入或审查
时，还要把未满足的规范要求与可选改进分开汇报。检查注释和随包 Markdown 中是否存在面向 Agent 的
命令，并把它们与合理的 API 要求和明确标注的使用建议区分开。
