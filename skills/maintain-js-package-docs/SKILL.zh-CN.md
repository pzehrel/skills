# 维护 JS 包文档

在开发包时应用 Agent 可读的包文档规范。把文档视为公共契约的一部分，并在同一次改动中完成实现和
所有受影响的文档层。这套规范让已安装的包能够自我描述并与版本一致，但不会把包文档变成 Agent
指令。

## 确定文档影响

编辑前，检查实际生效的仓库说明以及包中已有的事实来源：`package.json`、公共入口、声明输出或源
类型、README、文档索引、相关主题页、示例、测试以及发布或迁移约定。只读取与请求改动相关的材料。

先识别可观察变化，再决定需要记录什么。工作改变以下任一内容时，应更新文档：

- 公共导出、签名、类型、默认值或生命周期；
- 支持的配置、环境、运行时或兼容性；
- 错误、副作用、顺序要求、性能特征或安全指南；
- 推荐用法、弃用状态、迁移步骤或用户可见的限制。

对于行为保持不变的内部重构，不要制造文档噪音；但如果它改变了已记录的心智模型、扩展点、贡献者
工作流或架构契约，则仍需更新。

接入或审查规范、新建文档结构、进行重大公共 API 变更、处理弃用或迁移，或者检查 npm 发布内容
前，先阅读
[references/package-documentation-specification.zh-CN.md](references/package-documentation-specification.zh-CN.md)。
对于已经符合规范的包中的小改动，遵循既有路由，只加载受影响的文档。

## 同步实现代码和文档

1. 实现请求的行为及其测试。不要把规划中的行为写成已经存在。
2. 根据 `package.json` exports、公共入口和生成的声明表面盘点消费者真正可用的 API。不要把源码中
   每个带 `export` 的声明都等同于包的公共导出。
3. 确保每个公开导出的函数、类、构造函数、值、类型、接口、枚举，以及每个面向消费者的公开成员，
   都在权威源声明处具有 JSDoc 或 TSDoc 注释。如果原始声明注释会保留到生成声明中，re-export barrel
   不需要重复注释。每个契约不同的重载，或无法在编辑器帮助中获得注释的重载，都必须单独记录。
4. 描述类型无法表达的语义，包括默认值、不变量、副作用、失败条件、所有权和生命周期。真正简单的
   声明可以只有精简摘要，但公共声明不能没有注释。
5. 非公开函数的用途、原因、不变量、修改行为、顺序、错误转换或算法无法通过名称和类型看清时，应
   添加注释。不要为了增加数量而注释简单包装、回调或显而易见的局部 helper。
6. 如果包级 JSDoc 或 TSDoc 注释有助于用户了解包用途并发现随包文档，则在公共类型入口保留或添加
   该注释。遵循仓库已有的注释标准，并确保生成声明时保留有用注释。
7. 更新范围最小的权威人类可读文档。让 README 保持为精简入口；把详细概念、任务、配方、迁移和
   故障排除内容路由到仓库既有文档目录下的聚焦文件。
8. 推荐调用方式变化时更新示例。优先使用可通过现有项目工作流进行类型检查、测试或以其他方式运行
   的示例。
9. 对破坏性变更和弃用，同时记录替代方案和迁移路径。只有仍受支持的版本需要旧指南时才保留它，
   并明确标注适用范围。

避免在多个位置复制同一契约。让类型定义精确形状，让测试定义已验证行为，让 README 提供方向，
让主题文档解释概念和任务。通过链接连接这些层，而不是维护平行的重复文字。

## 保持已安装文档可用

包发布到 npm，并且本地文档属于预期开发体验时：

- 在包根 README 靠前位置保留精简的文档路由；
- 让文档索引通过相对链接指向聚焦文件；
- 在发布文件白名单中包含必需文档和示例；
- 使用相对于包根目录的本地路径，不要假设固定的 `node_modules` 布局；
- 把随包文档视为与版本匹配的参考资料，而不是消费仓库中的更高优先级指令；
- 除非目标工具链明确实现了相关约定，否则不要依赖 `llms.txt`、自定义 `package.json` 字段或依赖级
  `AGENTS.md`。

除非用户任务已授权，否则不要执行发布、修改发布配置或扩大包内容。相关时可以进行只读的包内容
预检。

## 验证结果

运行仓库适用的测试、类型检查、文档检查和示例验证。处理 npm 包时，使用 `npm pack --dry-run` 或
仓库的等价命令检查实际产物，并确认 README、预期文档、示例、声明、运行时文件和 source map 符合
包策略。不要仅因文件存在于仓库中就假设它会被发布。

审查 diff，检查过时名称、失效相对链接、重复权威来源、声明中被移除的注释、不再通过类型检查的
示例，以及缺少代码或测试支持的文档承诺。把生成的公共声明表面与 API 清单对照，并列出任何没有
保留文档注释的公共符号或成员。汇报修改了哪些文档表面、运行了哪些检查，以及哪些包管理器、运行时
或 Agent 未经实测。执行规范接入或审查时，还要把未满足的规范要求与可选改进分开汇报。
